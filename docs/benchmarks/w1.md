# W1 — storage benchmark: verdict

**Decision: GO.** ClickHouse as the single telemetry engine, with
`ORDER BY (tenant_id, resource_id, observed_at)` on every table, is confirmed by
measurement at 100 million rows. Three amendments were conditions of that go, and all
three are now in SPEC §M0.6 and implemented in `ch-migrations/`.

| | |
|---|---|
| **Ran** | September 2026 |
| **Subject** | ClickHouse 26.8.2.7, single node, Docker Desktop on Windows, warm cache, 5 iterations |
| **Scale** | 10 000 000 and 100 000 000 log rows, seed 42 |
| **Raw results** | [`bench/results/FINDINGS.md`](../../bench/results/FINDINGS.md) — every query, both scales |
| **Harness** | [`bench/`](../../bench) — generator, DDL, load and query scripts |

This document is the decision. The findings file is the evidence.

---

## What was being decided

PLAN §2 committed to **two storage engines rather than four**: PostgreSQL for the control
plane, ClickHouse for all telemetry — logs, metrics, traces and flows in one engine.
ClickHouse full-text search reached GA in March 2026, which is what made that possible at
all. The alternatives were rejected on paper: OpenSearch (roughly 10x the nodes at log
volume), Quickwit (Datadog-owned since January 2025), TimescaleDB for metrics
(557K → 159K rows/s at 10M hosts).

Rejecting alternatives on paper is cheap. The bet itself needed measuring, and it is a
specific one:

> **The Investigation Workspace.** "Show me every signal for `router-01` between 14:00
> and 14:15" must stay fast as the tenant's data grows, because that single query is what
> the product is *for*. Everything else — storage, polling, ingestion — is a commodity.

If that query degrades with table size, the architecture does not work, and no amount of
tuning later recovers it: the sort key is chosen at table creation and changing it is a
full re-ingest.

---

## The evidence

### The central bet, confirmed

**Q05 — all signals for one resource in a window — ran at 9 ms reading 16 380 rows at
10M rows, and at 9 ms reading 16 380 rows at 100M rows.**

Ten times the data. Identical latency, identical work. Resource-scoped investigation is a
function of how much *that resource* produced, not of how large the table is. Selective
token search behaves the same way: 8 190 rows read at both scales to find a single hit in
a hundred million.

That is the go, and it is why **the sort key must not change**.

### Everything else fell into exactly two groups

| behaviour | at 100M | examples |
|---|---|---|
| prunes (sort key or text index) | 9–230 ms | Q05, token search, filtered aggregates |
| reads the whole tenant | 403–2 378 ms | tail, histogram, `LIKE`, phrase, map `GROUP BY` |

Nothing in between. The dividing line is exactly *"can this query prune?"* — which made
the remediation obvious rather than a matter of tuning, and is why the amendments below
are structural rather than incremental.

---

## The three amendments that were conditions of the go

**1. The tail needs its own ordering.** "Newest N lines across the tenant" read the entire
tenant at 2 303 ms / 33.8M rows, because the sort key leads with `resource_id`. The
`p_by_time` projection makes it **72 ms / 254K rows — 32x**. Cost: ~1.9x storage on the
logs table, because time-ordering compresses ~58% worse than resource-ordering (4.79 GiB
vs 3.03 GiB for identical data). Budgeted, accepted, in `0002_logs_by_time_projection.sql`.

**2. The Explorer histogram needs pre-aggregation, and the projection does not help it.**
Measured: rows read barely moved (33.47M → 33.39M) with the projection in place, because a
histogram over the retention window touches every row whatever the sort order. Only
pre-aggregation helps. This matters more than the tail — it re-renders on every search and
every filter change, so its latency is felt per keystroke. `logs_counts_5m`, in
`0003_logs_counts_5m.sql`.

**Two fixes, two different root causes. Neither substitutes for the other** — which is
precisely the thing that would have been guessed wrong without measuring.

**3. Grouped attributes must be real columns.** The slowest query in the suite was not a
text search. It was `GROUP BY attributes['host.name']` at **2 252 ms**, worse than phrase
proximity, because a `Map` column decompresses in full for every row. `host_name` and
`service_name` are `MATERIALIZED` columns, and `uops_query::plan` rewrites onto them.

### Two further findings, folded in

**The text index costs 71% of compressed data at 100M**, and the overhead *grew* with
scale (67% → 71%) rather than amortising. Combined with the projection, a naive build
stores roughly 3x the raw compressed size — unacceptable on an on-premise customer's
finite disk array. Per-source opt-out is therefore **required**, not optional, and belongs
in the M2 monitoring profile schema.

**Substring and phrase search are not index-accelerated.** `LIKE` 1 928 ms and phrase
proximity 2 378 ms, both full tenant scans. ClickHouse 26.8 exposes
`use_text_index_like_evaluation_by_dictionary_scan`, which suggested `LIKE` might be
accelerated beyond what the GA announcement describes; it was not. Both modes still exist
in the Query AST because users need them, and both emit a `QueryWarning` so the UI can say
so before someone waits two seconds wondering why.

## What this verdict does not cover

Stated plainly, because a benchmark's limits are part of its result:

- **Scale beyond 100M rows.** 1B was not run. The two groups above are expected to hold —
  the pruning queries are size-independent by construction and the scanning ones are
  linear — but that is a projection, not a measurement.
- **Cold cache.** All numbers are warm, which is the right default for a monitoring
  platform whose query path is continuously exercised, but a first query after a restart
  is not represented here.
- **Concurrency.** Single-client. No measurement of what happens at N simultaneous
  investigations.
- **Metrics ingest and rollup cost.** The schema is in place and the rollup chain is
  correctness-tested (`scripts/ch.sh smoke`), but the write-throughput cost of maintaining
  the materialized views was not measured. Deferred to M4; tracked in STATUS.md.
- **Replication.** Single node. Nothing here speaks to a replicated or sharded deployment.

None of these change the go. Each would change a capacity plan, and none of them can
invalidate a sort key that is already proven size-independent.

## Harness artifacts — not ClickHouse numbers

Recorded so that nobody later mistakes them for storage limits:

- `docker exec -i` stdin load was **18x slower** than HTTP (182 s vs 9.9 s per 1M rows).
  Docker Desktop proxies container stdin through a named pipe that collapses under a
  high-rate stream. A harness property, not an ingest ceiling.
- `curl --data-binary @-` buffers the entire stream before sending: observed at 6.7 GB RSS
  and climbing toward ~32 GB on a 100M-row load, with zero bytes delivered server-side.
  Loads now run in bounded batches.

## Reproducing

The data is **regenerable and never committed**. Seed 42 reproduces it exactly.

```bash
docker compose -f bench/docker-compose.yml up -d
bash bench/scripts/load.sh logs 10000000 --truncate   # ~3 min
bash bench/scripts/run.sh 5                           # → bench/results/
```

---

## Sign-off

The architecture in PLAN §2 and SPEC §M0.6 is **accepted on measured evidence**, with the
three amendments above incorporated. The sort key
`(tenant_id, resource_id, observed_at)` is frozen: changing it is a full re-ingest, not a
migration, and the one number that justifies the whole design depends on it.

M0 proceeded on this basis, and the schema it produced is what
`ch-migrations/` applies today.
